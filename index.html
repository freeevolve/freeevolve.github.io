TL;DR

Agent evolvers edit the prompts, skills and workflows around a language-model agent, yet a human still designs the search loop they run in. FreeEvolve gives that loop to the evolver. It decides what to test, how much evidence to collect, which candidates to keep and when to stop. An editable evolution skill guides those decisions, and meta-evolution improves the skill by scoring the agents it produces.

Motivation

The search loop is still designed by hand

An evolver runs a target agent, reads its failures and edits its harness. Around that edit step sits a loop that someone wrote in advance.

The loop decides which tasks are evaluated, how often a measurement is repeated, how candidates are compared and when the search stops. Each choice encodes a guess about evaluation noise, task difficulty, useful curricula and available parallelism. Those guesses differ across agents and environments, and they go stale as evidence arrives. An evolver that only proposes edits cannot act on what it learns, so adapting the loop means re-engineering it by hand.

FreeEvolve moves each of those decisions inside the evolver.

Autonomy alone is not enough

Handing over control does not by itself produce a good campaign. With the hand-written seed skill, the evolver improves a fresh worker by at most 1.1 points. After meta-evolution, the frozen skill improves fresh workers by 2.2 to 13.8 points, and the skill learned on τ³-bench also improves ARC-AGI-2 and ARC-AGI-3.

Method

One invocation, two levels

A conventional evolver framework calls a proposer at fixed stages and keeps control of evaluation, selection and stopping. FreeEvolve invokes the evolver once, and the evolver stays in control until it returns an improved target.

The same interface works at two levels. At the agent level, the evolver improves a worker. At the meta level, the editable target is the evolution skill itself, and each candidate skill is judged by the workers its campaigns produce.

A bounded environment

Giving control to the evolver needs a clear boundary. Inside it the evolver can explore however it likes, but it cannot change the goal, the evaluation rules or the resource limits. An environment initialized with target \(x_0\) is

\[ \mathcal{E}[x_0] = \big(g,\ \mathcal{D},\ x_0,\ R_{\mathcal{E}},\ \mathcal{C}_{\mathcal{E}}\big) \]
  • \(g\)the improvement goal
  • \(\mathcal{D}\)the evolution data, e.g. the evolution split of a benchmark
  • \(x_0\)the initial editable target, e.g. the worker harness
  • \(R_{\mathcal{E}}\)runs candidate \(x\) under request \(u\) and returns an artifact bundle \(a = R_{\mathcal{E}}(x, u)\): scores, trajectories, logs
  • \(\mathcal{C}_{\mathcal{E}}\)the valid requests: benchmark rules and resource caps

The request \(u\) is where autonomy lives. The evolver picks which tasks to run, how many repetitions and seeds, and how much concurrency and time each execution gets. A prescribed loop fixes \(u\) before the run, so its evolver only ever sees \(R_{\mathcal{E}}(x)\) under one setting.

The evolver runs the whole campaign

The evolver is Claude Code equipped with a single markdown file of instructions, the evolution skill \(s\). A complete campaign is one call:

\[ x^\star = \mathrm{Evolve}\big(s;\ \mathcal{E}[x_0]\big) \equiv s\big(g,\ \mathcal{D},\ x_0,\ R_{\mathcal{E}},\ \mathcal{C}_{\mathcal{E}}\big) \]

The framework provides access to \(R_{\mathcal{E}}\) and takes no further role. The evolver decides which candidate to edit, which request to issue, how the returned artifacts change its next move and when to return \(x^\star\). Stable measurements let it move on, close comparisons justify more repetitions, and failures concentrated in one part of the data can be searched there before a candidate is validated broadly.

What is still written by hand

Two pieces, and neither is an evolution loop. Claude Code's own read, act, observe loop is generic tool use with no evaluation schedule, acceptance rule or stopping criterion. The seed skill fixes only dispositions:

  • Treat ENVIRONMENT.md as the source of truth and edit only the declared target.
  • Keep raw runs and make claims proportional to the evidence.
  • Use the available time and continue from the best-supported target.
  • Leave the strongest target under best/ with a short evidence summary.

Which tasks to evaluate, how many repeats to buy, when to branch and when to accept are left to the evolver.

Meta-evolution learns the campaign policy

Because the skill is a text file, meta-evolution needs no new machinery. A meta-environment makes the skill the editable target and uses worker environments as its data, \(\mathcal{D}^{\mathrm{m}} = \{\mathcal{E}^{\mathrm{w}}_i[w_i]\}_{i=1}^{n}\). A candidate skill has no score of its own. It is installed in an evolver, runs complete worker campaigns, and is judged by the workers and traces they produce:

\[ R_{\mathrm{m}}(s, u) = \mathrm{EvaluateWorkers}\Big(\big\{\mathrm{Evolve}\big(s;\ \mathcal{E}^{\mathrm{w}}_i[w_i]\big) : i \in I(u)\big\}\Big) \]
\[ s^\star = \mathrm{Evolve}\big(s_{\mathrm{outer}};\ \mathcal{E}^{\mathrm{m}}[s_0]\big) \]

The outer evolver edits \(s_0\), decides which inner campaigns to launch and reads their outcomes as feedback. \(s_{\mathrm{outer}}\) and \(s_0\) start as separate copies of the same seed, so editing the candidate never changes the controller. Meta-environments are excluded from their own data, which bounds nesting at two levels. The result is a frozen skill that can be installed in new environments without carrying over any source worker or campaign state.

What the evolver actually sees

One call to evolve.sh installs an environment in a fresh run directory and invokes the agent once. The meta-environment uses exactly the same layout.

$ ./evolve.sh --env arc_agi_3
run/
├── ENVIRONMENT.md    # goal, data, limits, how to read results
├── .target           # the editable surface x₀
├── run.sh            # R(x, u): run a candidate under request u
└── workspace-<env>/  # candidates, artifacts, notes (starts empty)

The environment files stay fixed for the whole campaign; only the declared target is editable. Evaluation always reads the declared edit surface, so the candidate being scored is the candidate being evolved.

Q2Does meta-evolution turn campaign autonomy into a stronger evolver?

Meta-evolution produces a better evolver

Each skill is frozen and installed on the same fresh base worker with the same resource budget. No evolved worker or campaign artifact carries over. The no-data variant asks an LLM to improve the seed skill without seeing any execution results.

The seed skill already improves workers, but only by 0.6 points on average across the four mean metrics. The meta-evolved skill adds a further 6.9 points, improves every available pass@3 metric and beats the no-data rewrite in every environment. The gain comes from execution experience. Rewriting the instructions without it does not reproduce the effect.

Q3Does the learned skill generalize beyond its source environment and model?

Learned skills transfer across environments and models

A skill captures how to organize improvement, not a particular worker, so it should be reusable. If it is, the compute-heavy meta-evolution runs once and the resulting evolver serves new environments. We freeze each meta-evolved skill and install it on a fresh worker in every target environment.

Transfer is positive on most target metrics. The τ³-bench skill reaches 64.3% on ARC-AGI-2 and 71.0 RHAE on ARC-AGI-3, matching or beating the skills meta-evolved on those environments directly. Both single-source skills lower the Terminal-Bench mean, which marks a boundary when the target's hardware and execution behavior change a lot. Meta-evolving on τ³-bench and Terminal-Bench 2.1 jointly gives a skill that improves every target metric over the seed.

Evolved workers run on cheaper models

Each method evolves its harness with the native Opus worker; the frozen harness then runs unchanged with Sonnet 4.6 and Haiku 4.5. FreeEvolve is the strongest harness in all six settings and keeps a 5.3-point average gain over the base harness on the four non-native ones, while several baseline gains on τ³-bench shrink or reverse. A worker can be evolved with a strong model and deployed with a cheaper one without re-evolution.

A stronger skill for fewer tokens

On ARC-AGI-3 we track the best training RHAE of the worker each method's skill produces against the total tokens spent to produce that skill, counting every evolver, evaluation and model call. FreeEvolve reaches 90.6 at 0.74B tokens. The best baseline stops at 81.7 after 1.3B.

Q4How does the evolver use campaign autonomy as evolution unfolds?

The campaign reorganizes itself as evidence arrives

Here is one ARC-AGI-2 worker-evolution campaign run under a frozen meta-evolved skill. Every marker is one evaluation on the evolution set, plotted against elapsed hours. None of the annotated moves is a stage of the framework. The evolver chose each one when the campaign called for it.

≈0.7 → 1.3 hUndo a regressionThree edits at once cost 0.18. It dropped two and kept the helper library, recovering 0.23.
≈1.4 hProbe cheaply15 rollouts on 2% of a round showed that a truncation came from the agent's own prompt rather than the platform.
≈4.9 hCombine discoveriesMerged the best-performing code so far with a good fix found in an underperforming run.
≈7.4 hBuy more evidenceDrew the same version three times and pooled the draws to confirm a gain.
≈12.2 hBranch the searchSplit an ancestor four ways: all three changes, hypothesis only, grids only, review only.

The harness it returned is not simply the highest single score. When choosing what goes in best/, the evolver weighs how many evaluations and paired comparisons back each candidate.

Removing one decision weakens the result

On τ³-bench we keep the learned skill and budget fixed and take away control of one execution decision at a time. Always evaluating the full set makes the evolver wait on expensive probes, so it makes fewer decisions within the time budget. A fixed concurrency of 24 or no task timeout leaves resources tied up by slow or failed executions; both spend more tokens and still produce a weaker worker. No single configuration is best. The benefit comes from being able to reorganize evaluation as the campaign unfolds.

What meta-evolution writes into the skill

Comparing the four meta-evolved skills with their common seed shows what was learned. The seed gives broad dispositions and leaves the organization of the campaign open. Meta-evolution turns those dispositions into operating rules for task selection, evaluation allocation and search control: use failures to choose new probes, move from cheap tests to confirmation only when warranted, and keep or combine changes according to accumulated evidence.

Q5What model capability does effective campaign control require?

Campaign control needs a capable model

We keep the τ³-bench worker and the meta-evolution setup fixed and change only the model that runs the evolver, from Haiku 4.5 to Opus 4.8.

Haiku 4.5 improves neither held-out metric: its evolution-split score climbs to 52.2 while held-out accuracy falls to 32.2. From Sonnet 4.6 onward, meta-evolution consistently improves held-out performance, and the strongest Opus models produce the best workers. Gains generally grow with newer and stronger models, although Sonnet 4.6 beats Opus 4.6.

Takeaway

The optimization process can be learned

Agent evolvers automated the design of harnesses but left the process that designs them in human hands. FreeEvolve automates that process too. The evolver runs its own improvement campaign inside a bounded environment, and meta-evolution learns from the outcomes how to run it. Across four environments the self-organized campaign matches or beats hand-designed evolvers, and the learned skill keeps improving with experience and transfers to new environments. What it carries is a way of running an improvement campaign, not domain knowledge.

Limitations

  • Held-out gains need a capable evolver model. Haiku 4.5 did not produce them; Sonnet 4.6 and stronger did.
  • Transfer weakens when the target's hardware and execution behavior differ a lot, as on Terminal-Bench 2.1.
  • Meta-evolution consumes substantial compute. Bounded nesting, retained evaluation records and separate acceptance make runs auditable, but they do not make autonomous improvement safe for high-stakes deployment.
